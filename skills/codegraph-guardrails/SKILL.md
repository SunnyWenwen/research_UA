# codegraph 查詢紀律(本專案)

> 這份文件**刻意不重複** codegraph MCP 在 `initialize` 時已經注入的操作說明

## 二、查詢紀律

### 1. 追呼叫鏈遇到介面時,要明確確認

codegraph 宣稱支援 `interface→impl` 的動態分派跳躍。但本專案大量使用
`@Autowired` 介面注入,**務必驗證那一跳是否真的出現**:

- 若 `codegraph_explore` 回傳了實作類別 → 可以繼續往下追
- 若只停在介面 → **明確告知使用者「此處有多個實作,圖上未區分」**,
  不要默默當成鏈路結束

### 2. 回答影響範圍時必須聲明限制

工具作者自己公布的實測數字:**Spring 框架的 route 覆蓋率是 83.3%**,
並註明那是「convention/reflection 重的框架的**誠實靜態分析天花板**」。

所以任何「這個改動會影響 X、Y、Z」的回答,都要附上一句:
> 以上為圖上可見的依賴。Spring 的靜態解析覆蓋率約 83%,
> 反射、DI 容器、框架慣例入口不在其中。

### 3. 剛改完程式碼要留意索引延遲

索引透過 file watcher 更新,**落後寫入約 1 秒**。
連續編輯後立刻查詢,可能拿到舊結果 —— 注意回應中的 staleness banner。

### 4. 符號名稱必須精確

`codegraph_explore` 的 call-path 查詢**要求精確匹配**,
拼錯或只給部分名稱不會被自動替換。若回報找不到並附上 did-you-mean 建議,
用建議的名稱重新查詢,不要自行猜測。

## 三、這張圖回答不了的問題

遇到以下需求,**明確告知使用者圖上沒有這些資訊**,改用其他方式:

| 問題 | 為什麼沒有 | 改用 |
|---|---|---|
| 「這個 API 最後寫到哪張資料表」 | 圖中**沒有資料表節點**。`@Entity` / `@Table` 註解、MyBatis XML 的 SQL 都不會變成節點 | 追到 Repository / Mapper 後,人工對照 Entity 註解或 mapper XML |
| 「前端哪個頁面呼叫這支 API」 | **無跨服務 / 跨語言連結**。HTTP 呼叫兩端都只是字串,沒有靜態關聯 | API 文件、或實際搜尋前端的 URL 字串 |
| 「這段 SQL 動到哪些欄位」 | SQL 不在圖的範圍內 | 直接讀 mapper XML 或 `@Query` |

## 四、禁止的推論

以下結論**不可以只憑這張圖做出**,必須明確拒絕或加上但書:

### ❌ 「沒有呼叫者,所以是死程式碼,可以刪」

以下情境都會讓實際有在用的程式看起來沒人呼叫:
- Spring Data 衍生查詢(`findByEmailAndStatus` 的實作是執行期 proxy 生成)
- 反射 / `Class.forName()` 載入
- `@EventListener` 事件接收端
- AOP 織入(`@Transactional`、`@Aspect`)
- 泛型容器取值後的方法呼叫

**正確回答方式**:「圖上找不到呼叫者,但以上情境不會出現在圖中,
刪除前請確認。」

### ❌ 「圖上只顯示這三支受影響,所以可以安全上線」

圖給的是**可見依賴的下限**,不是完整清單。變更影響評估仍需人工判斷與測試覆蓋。

### ❌ 拿圖當稽核或合規證據

自動建立的圖只能當輔助線索。需要完整性保證的場景(資安稽核、法遵盤點)
不可引用。

## 五、回答時的標註習慣

每次基於圖回答時,分清楚資訊來源:

- **來自圖的結構事實**(誰呼叫誰、檔案在哪)→ 可直接陳述
- **來自 `codegraph_explore` 回傳的原始碼**(逐字內容)→ 可直接陳述,
  並引用行號
- **你自己的推論**(這段程式的意圖、可能的副作用)→ 標明是推論

使用者需要知道哪些是機器解析出來的、哪些是你想的。
