三套程式碼知識圖譜的建與用

Understand‑Anything、graphify、codegraph 都說自己能「替 codebase 建知識圖譜」。 它們建出來的圖，可信度差很多。這份文件說明差在哪、以及各自適合什麼場合。

先講清楚：知識圖譜是什麼

node（節點）

程式裡的東西

一個 class、一個 method、一個欄位。有些工具還會有資料表。

edge（關係）

node 之間的關係

A 呼叫 B、A 繼承 B、A 引用 B。這才是圖的價值所在。

用途

讓 AI 看懂架構

不用把整個 repo 塞進去，就能回答「這支 API 會動到什麼」。

核心問題：node 容易，edge 很難

抓 node 很簡單 —— AST（程式碼的語法樹）裡白紙黑字寫著 class UserService， 解析器照著抄就好。

抓 edge 很難。AST 只告訴你「這一行有一個叫 findById 的呼叫」， 但不會告訴你那是哪一個 findById。大型專案裡可能有十七個同名 method， 分散在十七個 class。AST 本身給不出答案 —— 必須另外做型別推導。連錯一條，後面所有推論都跟著錯。

三套工具對這個問題，給了三個完全不同的答案：

Understand-Anything

不做型別推導，直接問 LLM：「你覺得是哪一個？」
快、什麼語言都能處理，但 LLM 猜錯了你看不出來 —— 圖上沒有任何記號區分「AST 抓的」和「LLM 猜的」。

graphify

從 AST 做型別推導。
查 userService 宣告成什麼 class，順著型別找到那個 class 裡的 method。推導不出來就不建 edge —— 寧可漏，不亂連。

codegraph

同樣從 AST 做型別推導，但多走一步。
如果變數宣告成介面，它會再往下找實作 —— 這正是 Spring 專案最需要的那一跳。

02

為什麼 edge 這麼難建

上一節說「差別全在 calls edge」。這一節說明為什麼那條 edge 這麼難， 以及三套各自走到哪一步就停了。理解這一節，才能判斷一張圖上「查不到」到底代表什麼。

建一條 calls edge，其實要走三段

看到 someVar.findById(id) 這一行，工具要回答的不是一個問題，是三個：

①

推出型別

someVar 是什麼型別？
要查這個變數的宣告 —— 可能在參數、在欄位、在上面幾行的區域變數。

→ UserRepository

②

型別找到 class node

專案裡叫 UserRepository 的 class 是哪一個？
同名的可能不只一個（不同 package）。

→ 唯一的那個 class node

③

class 找到 method node

那個 class 裡叫 findById 的 method 是哪一個？
overload 的話會有好幾個。

→ 建立 calls edge ✓

三段每一段都可能斷。graphify 的原始碼裡就有兩道明確的放棄閘門， 分別卡在第 ② 段（型別名對到多個 class）和第 ③ 段（overload）—— 遇到就直接不建這條 edge。

三套各走到第幾步

推 0 步

Understand-Anything

三段全部跳過，直接問 LLM 最終答案。
省掉的不只是型別推導，是整條驗證鏈。

推 1 步

graphify

變數 → 它的宣告型別。
走完三段就停，推不動就不建 edge。

推 2 步

codegraph

同樣走三段，但如果型別是介面，會再走一步找實作。
Spring 的 @Autowired 全靠這一步。

推導會在哪裡斷

以下六種，前兩種最常見。第 ③④ 種三套都沒做 —— 是共同的天花板。

情況Java 例子為什麼斷誰過得了
① 宣告成介面 @Autowired
private UserService userService;
userService.findById(id);		 型別推導成功了，推到 UserService。但那是介面，findById 只有簽章沒有實作內容。 只有 codegraph 會再走一步找實作類別。graphify 停在介面。

Spring 專案幾乎全中這一類。
② overload findById(Long id)
findById(String code)		 要選對得比對參數型別。 graphify 直接放棄不建 edge
③ 泛型取值 List<User> users;
users.get(0).getName();		 讀 List<User> 時只取得到基底型別 List，拿不到裡面的 User。（已查證程式碼） 三套都沒做泛型代換
④ 回傳值串接 getRepository().findById(id); 型別表只記「變數 → 型別」，沒有記「method → 回傳型別」，所以 getRepository() 推不出來。 三套都沒做
⑤ 型別不在索引裡 第三方 jar、JDK 的 class 看不到它們的原始碼，找不到對應的 node。 都不行（設計如此，不是缺陷）
⑥ 反射 Class.forName(name) 執行期才決定，靜態分析理論上就不可能。 都不行

不是每種 edge 都需要型別推導

這是常見的誤解。大多數 edge 的目標字面就寫在那一行，不用推。 但「寫在那裡」不代表「知道它指向哪一個 node」—— 名字是會撞的。

目標端怎麼來哪些 edge風險
讀出來結構 contains file 裡有 class、class 裡有 method —— 就是 AST 的巢狀結構。零風險。
讀出來名字寫在那裡 imports extends implements instantiates decorates extends BaseEntity、new UserDTO() —— 型別名是字面寫著的，不用推。

⚠ 但專案裡可能有三個 BaseEntity（在不同 package）， 要選對得靠檔案頂端的 import 敘述。這叫 import 綁定，同樣是一道會斷的關卡。
推出來 calls（x.foo() 這一類） 要走完前面那三段。Java 幾乎所有呼叫都屬於這一類 —— 所以型別推導的品質，基本上就決定了 Java 專案圖的品質。
猜出來 裸名字比對、LLM 推測 永遠有答案，而且不會告訴你答錯了。

graphify 明確拒絕「猜出來」那一格

它的原始碼註解寫著：缺少或模糊的接收者型別會被跳過，而不是退回裸方法名比對。

另一處在講為什麼要阻擋跨語言比對：「沒有這個，Java 的 Greeter 會 很開心地綁到另一個 repo 的同名 Python 類別。」

「很開心地」這個用詞很傳神 —— 純名字比對永遠找得到東西，這正是它危險的地方。

回頭看 UA：為什麼會變成這樣

UA 不是偷懶。它的 calls edge 之所以交給 LLM，是一個架構決定的連鎖結果：

1

決定讓 LLM 逐檔分析

2

每次只看得到一個檔案

3

解析器抓呼叫的資料結構就設計成逐檔的 —— 只有「誰呼叫誰」和行號，沒有欄位記「對方在哪個檔案」

4

跨檔案的呼叫沒地方存

5

只好在 edge 規格裡寫：「這個檔案裡的函式呼叫了另一個檔案的函式 —— 從 import 和函式名稱推測」

!

而且整張圖都是 LLM 直接產出 JSON —— 專案裡曾經有一層用程式建圖的 TypeScript 程式碼（含正確的跨檔案建邊函式），整層已經棄用、零呼叫點。建圖的職責整個移交給了 LLM

所以根因是「逐檔分析」這個架構決定，型別推導只是被連帶犧牲的東西。

這也解釋了一個看似矛盾的現象：UA 的 import edge 反而做得特別紮實（有一支 2000 多行的專用程式處理路徑別名、套件設定檔）—— 因為那支程式是全域跑一次的，不受逐檔限制。 同一個專案裡，不受架構限制的部分做得很好，受限制的部分就整段外包給 LLM。

UA 的 edge 到底是誰建的

「node 用 AST、calls 用 LLM」這個講法太粗。 實際上 UA 沒有任何一條 edge 是程式直接寫進圖的 —— 全部經過 LLM。差別在於 LLM 手上有沒有程式算好的答案可以照抄，以及事後有沒有人去對答案。

兩層都有 · 最終是確定性的

imports

(a) 內容解析　一支 2000 多行的專用程式，全域跑一次，把 "./utils"、"@/lib/auth"、"com.foo.Bar" 這類字串解析成實際檔案路徑

(b) 建完校正　merge 階段拿那份對照表逐筆比對，把 LLM 漏掉的補回來，補上的標記 recoveredFromImportMap

只有第一層 · 漏了沒人知道

contains　exports

(a) 內容解析　tree-sitter 抓出本檔案的 function / class 清單 ✓

(b) 建完校正　沒有。結構資料確實被寫成檔案（tmp/ua-file-extract-results-N.json），但 merge 階段從來沒去讀它 —— 不是拿不到資料，是沒接上

兩層都沒有

calls　inherits　implements　depends_on　tested_by

(a) 內容解析　沒有。LLM 只拿到一份「鄰居檔案的 exported symbols 清單」，要自己比對名字決定連哪一個

(b) 建完校正　只有一個「把指向不存在節點的 edge 丟掉」的守門 —— 驗證目標存在，不驗證目標正確

LLM 連「照抄」都會漏掉約 25%。
這不是我們的推測，是 UA 自己寫在 merge 程式碼註解裡的量測值： 「file-analyzer agent 被要求 1:1 謄寫成 edge， 但實際在真實專案上會漏掉約 25%」。

而且這是在最嚴格的條件下量到的 —— 規格明文寫著 「Not 90% of it. Not "the meaningful ones". All of them.」， 還要求 agent 自行加總核對。即使這樣，還是漏四分之一。

所以那個 recovery pass 不是保險，是必需品。 而 contains 走的是完全同一條謄寫路徑 —— 沒有理由相信它不會漏，只是沒有基準可以發現，也沒有東西去補。

他們曾經把一條 edge 從 LLM 換成程式

那支 import 解析程式的檔頭註解寫著：

「取代了 agents/project-scanner.md 裡由 LLM 撰寫的 prose 版 import 解析器 （原本的做法是用文字描述各語言的模式；執行期的 LLM 產出的是不一致、只會寫 regex、覆蓋率稀疏的腳本）。」

這一段同時證明三件事：

  • 他們知道 LLM 產的 edge 不可靠 —— 而且有實測的失敗經驗
  • 他們有能力也真的動手把一條 edge 從 LLM 改成確定性程式
  • 但還沒對 calls 做同樣的事

為什麼偏偏是 import 被補起來？

因為 import 的漏失看得出來。 importMap 是一份完整的「檔案 → 目標檔案」對照表，可以逐筆比對； 而且 import 是整張檔案依賴圖的骨幹，漏掉四分之一的話，畫面上的圖會明顯斷裂。

相對地，contains 少一個 function 節點的連線，圖看起來完全正常； calls 漏掉或連錯，更是完全無法察覺。

被修的，剛好是漏掉會被肉眼看出來的那一條。 這不是針對 UA 的批評 —— 這是自動建圖的通則： 你只會修你量得到的東西；量不到的那些，不會因為沒人抱怨就是對的。

UA 還缺兩條關鍵 edge

前面講的是 calls edge 怎麼來。但 UA 還少了兩種 edge —— graphify 和 codegraph 都有，而它一條都沒有。 一條壞掉類別內的導航，一條壞掉跨符號的影響評估。

缺口 1

class → method　誰屬於誰

UA 的 contains edge 全部是 file → function 和 file → class —— class 和 method 在圖上是平輩，都掛在檔案底下，彼此沒有連線： 

file:UserServiceImpl.java
  ├─ contains → class:UserServiceImpl
  └─ contains → function:findById      ← 跟 class 平輩，沒有連線

所以這些問題在 UA 的圖上答不出來：

  • 「UserServiceImpl 這個 class 有哪些 method」
  • 「findById 屬於哪個 class」
  • 「改 BaseEntity 會影響它子類別的哪些 method」

只能靠檔案路徑間接推論 —— 而一個檔案有多個 class 時就失效 （Java 的 inner class、一個檔案放 DTO + Builder、Kotlin 的多 class 單檔）。

這條缺口解釋了一件更根本的事。
graphify 的 method 索引是用 (class node, method 名稱) 當 key —— 沒有 class → method 這層關係，型別推導的第 ③ 段本來就走不了。 推到 class 之後無處可去。

所以 UA 不做型別推導，不只是「選擇不做」，是圖的結構上做不了。

最可惜的是：AST 其實抓到了。 UA 的結構分析結果有一個 owner 欄位（宣告這個 function 的型別）， 各語言的 extractor 真的有填 —— Go 填 receiver type、C++ 填 className、Rust 填 impl 的型別， 三態語意也設計過（空字串＝自由函式、null＝抓不到）。

它被用在增量更新的變更偵測和符號驗證上， 唯獨沒被用來建 edge。資訊抓到了，在建圖那一步被丟掉。

缺口 2

references　誰用了這個符號

UA 只有 calls 和 imports。但以下這些都不算 call、也不算 import： 

private UserStatus status = UserStatus.ACTIVE;   // 引用一個 enum 常數
void process(OrderDTO dto)                       // 型別被當參數
return new ArrayList<UserVO>();                  // 型別當泛型參數
@Value("${app.timeout}")                         // 引用一筆設定

在 graphify 裡 references 是第二高頻的關係類型 （54 個產生點，僅次於 contains）—— 因為它回答的正是日常最常問的問題。

後果很具體。「我要改 OrderDTO，誰會受影響？」

工具答得出什麼
graphify 列出所有把它當欄位、參數、回傳值、泛型參數的符號。還可以用 context 只看其中一類
codegraph 同上，而且型別關係另外存成獨立的 edge，語意更明確
UA 只答得出「哪些檔案 import 了它」

粒度從「符號」掉到「檔案」。 一個 500 行的檔案 import 了 OrderDTO，你還是得整個讀完才知道哪裡用到 —— 而這正是知識圖譜本來要省掉的工。

兩條缺口合起來看：class → method 讓圖往內看不清（類別的組成）， references 讓圖往外看不清（符號的使用者）。 剩下的 calls 又是 LLM 猜的 —— 所以 UA 的圖真正紮實的部分，其實只有 file → file 的 import 關係。

跨語言的 edge：只有一條，而且有但書

前面談的都是同一種語言內的 edge。那前端呼叫後端 API、 Java 服務呼叫另一個 Java 服務 —— 這類跨越語言或跨越服務的關係，三套接得起來嗎？

工具跨語言實際情況
Understand-Anything 沒有機制 LLM 只看得到「自己批次的檔案」加上 neighborMap。 而 neighborMap 是從 import 關係建的 —— import 不跨語言，所以 neighborMap 也不會。
它理論上可以亂連，但沒有任何路徑會讓它看到跨語言的一對。
graphify 刻意阻擋 原始碼註解：「沒有這個，Java 的 Greeter 會 很開心地綁到另一個 repo 的同名 Python 類別。」
這是選擇，不是缺陷 —— 純名字比對跨語言的誤連率太高。
codegraph 有一條 JS/TS 的 HTTP 呼叫 → 任何語言的 route。
它的設計思路寫在註解裡：「一個 web app 是兩個程式在一條圖看不見的線上對話…… 每一跳兩邊都是字串，而那個字串就是把它接起來的證據。」

codegraph 那一條怎麼跨得過去

兩個關鍵設計讓它與語言無關：

①

route 索引不分語言

建索引時直接取所有 route 節點，沒有語言過濾。而 Spring 的 @GetMapping / @PostMapping、class 層級的 @RequestMapping 前綴、甚至路徑裡的 static final String 常數， 都會被解析成 route 節點（Java 和 Kotlin 都支援）。

②

參數語法涵蓋多個生態系

比對路徑時，參數段的規則同時認得四種寫法：

:param   ← Express / NestJS
{param}  ← Spring / JAX-RS
[param]  ← Next.js
<param>  ← Flask / Django

{ 就是為 Spring 的 /users/{id} 準備的。

所以一個 TypeScript 前端的 fetch('/api/users', { method: 'POST' })， 真的可以連到一個 Java Spring 的 @PostMapping("/api/users")。 這條 edge 會標成 推測， 並記下 tier: 'client→server' 與 route 的註冊位置。

但書：發起端只掃 JS/TS 檔案

整段掃描的第一行就把非 JS/TS 的檔案跳過了 —— 副檔名限 .js .jsx .ts .tsx .mjs .cjs .mts .cts。

情境接得起來?為什麼
TS 前端 → Java Spring API✅發起端是 TS，目標是 route 節點
Java 服務 → 另一個 Java 服務
（RestTemplate / WebClient / Feign）		❌發起端不是 JS/TS，直接被跳過
Java → Python API❌同上

另外兩條通道（queue job、event bus）看起來是 NestJS / Bull 專屬 （@Processor、@InjectQueue、@OnEvent、@SubscribeMessage），兩端都要 JS/TS。

所以純 Java 的微服務架構，這條路徑用不上 —— 除非同一個 repo 裡有 JS/TS 前端。 Java 服務之間的呼叫，三套都接不起來。

通則：跨語言不是「做不到」，而是只有在 兩邊都留下同一個字串、而且工具剛好認得那兩種寫法時才做得到。

codegraph 做了 HTTP 這一條（發起端限 JS/TS）， graphify 刻意不做（避免同名誤連）， UA 連機制都沒有。

順帶一個陷阱：weight 不是 confidence

UA 的 edge 規格表給每種 edge 一個固定的 weight：

imports  → 0.7    ← 來自確定性的 import map，最可信
calls    → 0.8    ← LLM 推測，最不可信

最可信的 edge 權重反而最低。因為 weight 是「這種 edge 類型的固定分數」， 跟「這一條是不是真的」完全無關。

如果有人想用 weight 過濾可信度，會剛好篩掉最可靠的、留下最可疑的。 這是個很具體的例子：圖上有數字，不代表那個數字有意義。

04

三個實際踩到的坑

這三個都是實際操作驗證過的，不是理論推測。分享時值得提，因為它們說明一件事： 全自動建出來的圖，有些缺失是看不出來的。

坑 1 — 圖上查不到，不代表真的沒有

我拿一份典型的 Oracle DDL 測 graphify：三張表都建出來了， 但外鍵一條都沒有。

原因不是資料庫沒有外鍵，而是解析器看不懂 VARCHAR2 和 NUMBER(10,0) 這些 Oracle 專有寫法，整個欄位區塊解析失敗，寫在裡面的外鍵一起消失。

最麻煩的是它不會報錯 —— 表的數量完全正常，你不會知道少了什麼。 （已寫好前處理腳本可修正。）

坑 2 — 「找不到路徑」可能只是方向記反了

graphify 查兩點之間的路徑時，預設只往一個方向找。找不到會回「沒有路徑」。

但依賴注入、callback 註冊這類關係，該記哪個方向本來就是模糊地帶。 工具記反一條，查詢就直接說「沒有」。

實務規則：查不到時先換成「不分方向」再試一次，才能下結論。

坑 3 — 查詢結果沒有先後順序

查出來的那串 node，只代表「這些跟你問的有關」，不代表執行順序。 「A 和 B 相關」不等於「A 呼叫 B」。

要順序得另外查：graphify 用「最短路徑」功能，codegraph 看報告開頭的呼叫鏈。 別讓 agent 從 node 清單自行推論流程。

結論

Understand-Anything

node 是 AST 的，edge 是 LLM 的。

適合「快速認識一個沒碰過的 repo」。不適合任何需要「不會漏」的場合 —— 因為 calls edge 是 LLM 猜的，而且你分不出哪些是。

graphify

寧可漏，也不亂連。

唯一有信心分級的。適合看架構全貌（有模組分群、核心元件排行、PR 影響分析）。代價是 agent 拿到 node 清單後還要自己讀程式碼。

codegraph

直接把答案和原始碼一起給你。

適合追一條具體的鏈路、問「改這裡會影響誰」。省來回、答得準，代價是幾乎沒有旋鈕可以調。

真正的差別：把多少判斷交給 AI

三套的差別不在「誰的圖比較準」，而在把哪些判斷交給 AI。 交得越多，彈性越大、但錯了越沒有痕跡；交得越少，答案越穩、但你越無法客製。

codegraph graphify Understand-Anything
工具說了算：兩個參數，回傳成品 AI 說了算：自訂搜尋，自行推論

給決策者的一句話

本文描述的是三套工具的設計與實作，不是它們在我們 codebase 上的實測覆蓋率。

要談覆蓋率，需要另外做抽樣驗證 —— 而且一定要做。 坑 1 就是最好的例子：一份看起來完整、實際缺了一整類關係的圖， 光看數字是看不出來的。

查證方式 — 本文每一項結論都對照過三套工具的原始碼； Oracle DDL 的部分是實際安裝解析器跑過真實語法後的結果。
需要檔案行號層級的佐證，可另外索取技術版。
