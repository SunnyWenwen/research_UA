程式碼知識圖 · 查詢階段架構分析

三種查詢架構

圖建好之後才是真正的分歧點。Understand-Anything、Graphify、CodeGraph 對「agent 該怎麼用這張圖」給了三個互不相容的答案。

內容依據三個專案的原始碼實際查證:UA 的 skills/understand-chat/SKILL.md、Graphify 的 references/query.md 與 serve.py、CodeGraph 的 src/mcp/server-instructions.ts 與 src/installer/targets/opencode.ts。

UNDERSTAND-ANYTHING

LLM 是遍歷器

不提供查詢引擎。skill 教 agent 用自己的 grep 工具去掃 JSON 檔,關係由 LLM 自己拼。

GRAPHIFY

程式遍歷,LLM 組答案

CLI 跑 BFS/DFS 回傳子圖,LLM 負責解讀與敘述。查詢前強制做詞彙擴展。

CODEGRAPH

程式做完,一次給完

單一 MCP 工具,一次回傳逐字原始碼 + 呼叫路徑 + 影響範圍。明令 agent 不要再驗證。

查詢管線

同一個問題「這個 Controller 怎麼走到 Repository」,三者走完全不同的路徑。標色的步驟是各自架構的關鍵動作。

Understand-Anything

.ua/knowledge-graph.json

  1. 解析資料目錄 $UA_DIR
  2. 檢查新鮮度 — 比對圖的 git commit 與 HEAD、staged、working tree、未追蹤檔
  3. Grep "project" 區段取專案資訊
  4. Grep 節點 — 掃 name / summary / tags 欄位,記下命中的 node id
  5. Grep 邊 — 拿那些 id 再掃一次 edges 區段
  6. Grep "layers" 取架構分層
  7. LLM 依手上的片段組出答案
深度上限:1-hop。skill 原文:「This gives you the 1-hop subgraph」,沒有第二輪。

Graphify

graphify-out/graph.json

  1. 確認 graph.json 存在
  2. 詞彙擴展(強制) — 抽出圖上所有節點標籤的 token,跟使用者的用詞比對,組出真正能命中的查詢字串
  3. 執行遍歷 — graphify query "擴展後的字串",BFS 或 DFS
  4. CLI 不可用時,改用 NetworkX 在記憶體裡跑同樣的遍歷
  5. 依 token budget 排序截斷
  6. LLM 依子圖組出答案,引用 source_location
深度可調。另有 path(最短路徑)與 explain(單節點)兩個獨立指令。

CodeGraph

.codegraph/codegraph.db

  1. OpenCode 啟動時 spawn codegraph serve --mcp
  2. 指南自動注入 — MCP initialize 回應夾帶操作說明,直接進 system prompt
  3. 單次工具呼叫 — codegraph_explore("問題或符號名")
  4. SQLite 查詢引擎解析,次毫秒回應
  5. 一次回傳三樣 — 逐字帶行號原始碼、符號間的呼叫路徑、影響範圍摘要
  6. LLM 直接用,不再讀檔
回傳即 Read。格式與 Read 工具相同,可直接拿去 Edit。

三個關鍵分歧

一、遍歷交給誰

這是最根本的一條。UA 把遍歷交給 LLM —— 兩次 grep 之後,要不要再追一層、追哪裡,都是模型臨場判斷。好處是彈性,壞處是深度和完整性每次都不一樣,而且無法驗證。

Graphify 和 CodeGraph 都把遍歷交給程式。差別在 Graphify 回傳的是「子圖」,LLM 還要自己把節點和邊翻譯成人話;CodeGraph 直接回傳原始碼,LLM 只需要讀。

二、一個工具還是一組工具

CodeGraph 只暴露 codegraph_explore,其他七個工具預設隱藏。原始碼的理由不是簡化,而是實測:

Measured agent behavior showed that one strong tool steers agents better than a menu of narrower ones — fewer mis-picks, and it saves context every session.

Graphify 的 MCP 模式走相反路線,給十個工具讓 agent 自己挑。兩種設計沒有絕對優劣:工具多,表達力上限高;工具少,agent 選錯的機會低。

三、agent 該不該再驗證

CodeGraph 在注入的指南裡明確要求 「Trust the results — don't re-verify with grep」。這句話成立的前提是:它回傳的是逐字原始碼,不是摘要,所以沒有再驗證的必要。

UA 的情況相反且值得警惕 —— 它的節點帶著另一個 LLM 在建圖時寫的 summary。agent 看到那段摘要容易覺得「懂了」就直接回答,但那句話可能不準、可能過期,而且讀起來很權威。Graphify 和 CodeGraph 的節點只有 AST 抽出的識別字與行號,少一層轉述,也就少一層失真。

一個容易忽略的依賴

UA 的查詢品質取決於你用的 agent 的 grep 工具長什麼樣,這點在選型時幾乎沒人算進去。

它的圖是縮排 2 的 JSON,一個欄位一行。所以 grep "name": "getUser" 只會命中那一行 —— id、filePath、summary 全在別的行。

OpenCode 的 grep 工具參數只有 pattern / path / include / limit,沒有任何取得上下文行的選項,底層 ripgrep 呼叫也不帶 -A/-B/-C。Claude Code 的 Grep 則有完整的上下文參數。

同一張 UA 圖,換一個 agent,能撈到的資訊量就不同。Graphify 和 CodeGraph 沒有這個問題 —— 它們回傳的是完整的結構化結果,不受宿主工具能力影響。

選型結論

日常查詢

CodeGraph。回合數最少、token 最省、回傳即可編輯。單一工具的設計讓 agent 幾乎不會選錯路徑。代價是表達力被框死 —— 預設沒有自訂查詢的出口。

架構概觀

Graphify。god_nodes、get_community、shortest_path 這些高階原語適合「這個系統長怎樣」類的問題,社群分群也是它獨有的。查詢前的詞彙擴展對非英語使用者特別有價值。

不建議作為查詢層

Understand-Anything。1-hop 限制、依賴宿主 grep 能力、節點摘要由 LLM 生成 —— 三項疊加讓查詢結果難以預期。它的新鮮度檢查設計得最完整,那個機制值得其他工具借鑑。

三者的取捨可以用一句話收攏:把多少決策權留給模型。UA 留最多,CodeGraph 留最少,Graphify 在中間。決策權越少,結果越可預期;決策權越多,遇到預設路徑覆蓋不到的問題時越有轉圜餘地。

沒有一種配置對所有問題都最好,但對「每天問幾十次、答案要能直接拿去改程式碼」這種主流用途,可預期性的價值高過彈性。
