程式碼知識圖 · 能力邊界評估

靜態分析的盲區

全自動建立的呼叫鏈圖譜,在哪些情境下會斷掉 —— 以及為什麼那不是工具的缺陷,而是靜態分析本身的邊界。

案例分類依據 graphify 的 Java 解析器原始碼(extract.py 的 _resolve_java_member_calls)實際的放棄條件,以及靜態分析的一般性限制。程式碼範例為典型 Spring Boot 結構。

核心結論:自動建立的知識圖可以大幅加速「理解既有系統」,但不能當作影響範圍的完整性保證。

圖上「有」的邊,可信度高 —— 好的工具寧可漏抓也不亂連。但圖上「沒有」的邊,不代表程式碼裡真的沒有這條關係。用它來回答「這段程式在做什麼」很有效;用它來回答「我改這裡會不會漏掉什麼」則必須搭配人工複核。

一、型別推導不到 需完整型別推論

工具知道「這裡有一個方法呼叫」,但不知道被呼叫的物件是什麼型別,因此無法決定要連到哪個類別的方法。多數工具只查「宣告出來的型別」,推導不出「算出來的型別」。

鏈式呼叫

OrderService ──✓──▸ getRepository() ──✕ findById() 從此無法追蹤
// 前半段查得到,後半段查不到
orderContext.getRepository().findById(id);
//             ↑ 回傳型別要推導,不是宣告出來的

圖上會看到:到 getRepository() 為止,之後整條鏈消失。使用者以為 Repository 沒被呼叫。

泛型容器取值

list ──✓──▸ get(0) ──✕ getName() 不知道回傳的是 User
List<User> users = repo.findAll();
users.get(0).getName();
//   ↑ 要做泛型替換才知道 get(0) 回傳 User

圖上會看到:User.getName() 看起來沒有任何呼叫者。在死程式碼盤點時會被誤判為可刪除。

型別推論變數與 Stream

var handler = factory.create(type);   // var 沒有寫出型別
handler.process(payload);

orders.stream()
      .map(Order::getCustomer)         // method reference
      .forEach(this::notify);          // 執行期才綁定

圖上會看到:Stream 管線裡的每一個方法引用都是斷點。現代 Java 越常用函數式寫法,漏抓越多。

二、執行期才決定 理論上不可判定

這一類不是工具做不好,是任何靜態分析都不可能做到 —— 因為答案在程式跑起來之前根本不存在。這是計算理論層級的限制,換工具、換廠商都無解。

介面注入 + 多實作

CheckoutService ──✓──▸ PaymentGateway(介面) ──✕ 實際跑的是哪一個實作?
@Autowired
private PaymentGateway gateway;   // 介面

gateway.charge(order);
// 實作可能是 CreditCardGateway / LinePayGateway / MockGateway
// 由 Spring 依 @Profile、@Qualifier、設定檔在啟動時決定

圖上會看到:邊只連到介面,不會連到任何實作類別。追「這筆付款最後走哪段程式」會在介面處停住 —— 而這通常正是最需要追的地方。

框架執行期生成的方法

public interface UserRepository extends JpaRepository<User, Long> {
    List<User> findByEmailAndStatus(String email, Status status);
    // ↑ 沒有方法體。Spring 在啟動時用 proxy 動態生成 SQL
}

圖上會看到:方法宣告存在,但沒有任何實作可連。程式碼裡從來不存在那段查詢邏輯,靜態分析自然找不到。

反射與動態載入

String className = config.get("handler.class");
Class<?> clazz = Class.forName(className);
clazz.getMethod("execute").invoke(instance, args);
// 呼叫目標寫在設定檔裡,編譯期完全不可見

圖上會看到:完全沒有這條邊。舊系統的外掛機制、規則引擎、workflow 引擎大量使用這種模式。

AOP 與事件驅動

@Transactional            // 交易邏輯由 AOP 織入,原始碼裡看不到
@Retryable
public void submitOrder(Order o) {
    publisher.publishEvent(new OrderCreatedEvent(o));
    // ↑ 誰接收?由 @EventListener 註冊,執行期才配對
}

圖上會看到:發布端和接收端是兩座孤島。事件驅動架構用得越多,圖的連通性越差。

三、跨越系統邊界 超出單一工具範圍

呼叫鏈離開了程式語言本身,進入資料庫、網路、訊息佇列。每跨一次邊界就需要一套額外的專屬解析邏輯,而多數通用工具只做到語言邊界為止。

程式碼到資料表

UserRepository ──✓──▸ User(Entity) ──✕ table: users
@Entity
@Table(name = "users")      // 表名寫在註解的字串參數裡
public class User { ... }

圖上會看到:程式碼節點和資料表節點是兩張互不相連的圖。要打通必須有針對 JPA / MyBatis 的專屬解析(部分工具有,通用工具多半沒有)。

服務之間的呼叫

restTemplate.postForObject(
    "http://order-service/api/v1/orders", req, Resp.class);
// 對應到另一個 repo 的 @PostMapping("/api/v1/orders")

圖上會看到:單一 repo 的圖到此為止。微服務架構下,一個業務流程的完整鏈路天生被切成好幾段。

四、工具刻意放棄 設計取捨

這一類工具「有能力猜,但選擇不猜」。graphify 的原始碼註解寫得很直接:缺少或有歧義的 receiver 型別會被略過,而非退回用純方法名比對。這是刻意的取捨 —— 寧可漏抓,也不要給出可能是錯的答案。

方法多載

notificationService.send(user);
notificationService.send(user, Channel.SMS);
notificationService.send(user, Channel.SMS, priority);
// 三個同名方法 → 工具無法確定是哪一個 → 整個放棄

圖上會看到:三條邊一條都不會出現。企業系統裡多載很常見,累積起來的漏抓量可觀。

同名類別與第三方程式庫

// 兩個 package 都有 User → 歧義 → 放棄
com.acme.billing.User
com.acme.identity.User

// 型別定義在 JAR 裡,不在專案原始碼 → 無法解析
redisTemplate.opsForValue().set(key, value);

圖上會看到:沒有邊,但也不會有錯的邊。這正是取捨的價值 —— 你可以信任圖上有的東西。

所以該怎麼用

  • 適用

    快速理解陌生模組。新人上手、接手舊系統、盤點某個功能牽涉哪些檔案 —— 圖給的起點比 grep 快一個量級,而且附帶行號可以直接跳過去讀原始碼。

  • 適用

    架構層級的概觀。哪些模組是樞紐、系統大致分成幾個子系統、模組之間的依賴方向 —— 這些結論不依賴每一條邊都完整。

  • 適用

    縮小人工複核的範圍。把「要讀 300 個檔案」變成「先讀這 12 個」,人工仍然要做,但成本降下來了。

  • 不適用

    當作影響範圍的完整清單。「圖上顯示只影響這三支程式,所以可以安全上線」—— 這個推論在上面任何一種情境下都會出錯。變更影響評估仍需人工判斷與測試覆蓋。

  • 不適用

    當作死程式碼的判定依據。「沒有任何呼叫者,所以可以刪」—— 泛型、反射、DI、事件驅動都會讓實際有在用的程式看起來沒人呼叫。

  • 不適用

    當作稽核或合規證據。需要完整性保證的場景(資安稽核、法遵盤點),自動建立的圖只能當輔助線索,不能當作證明。

盲區的分佈與程式碼風格高度相關:大量使用介面注入、事件驅動、反射的系統,自動建圖的覆蓋率會明顯低於以直接呼叫為主的系統。建議在導入前,先在自己的程式碼庫上抽樣驗證幾條已知的關鍵鏈路,用實測數字取代通則。
