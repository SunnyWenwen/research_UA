# 三套程式碼知識圖譜的建與用

> Understand-Anything、graphify、codegraph 都說自己能「替 codebase 建知識圖譜」。
> 它們建出來的圖，**可信度差很多**。這份文件說明差在哪、以及各自適合什麼場合。

---

## 先講清楚：知識圖譜是什麼

| | 是什麼 | 說明 |
|---|---|---|
| **node（節點）** | 程式裡的東西 | 一個 class、一個 method、一個欄位。有些工具還會有資料表。 |
| **edge（關係）** | node 之間的關係 | A 呼叫 B、A 繼承 B、A 引用 B。**這才是圖的價值所在**。 |
| **用途** | 讓 AI 看懂架構 | 不用把整個 repo 塞進去，就能回答「這支 API 會動到什麼」。 |

### 核心問題：node 容易，edge 很難

抓 **node** 很簡單 —— AST（程式碼的語法樹）裡白紙黑字寫著 `class UserService`，解析器照著抄就好。

抓 **edge** 很難。AST 只告訴你「這一行有一個叫 `findById` 的呼叫」，
**但不會告訴你那是哪一個 `findById`**。大型專案裡可能有十七個同名 method，分散在十七個 class。
**AST 本身給不出答案** —— 必須另外做型別推導。連錯一條，後面所有推論都跟著錯。

**三套工具對這個問題，給了三個完全不同的答案：**

| 工具 | 做法 |
|---|---|
| **Understand-Anything** | **不做型別推導，直接問 LLM：「你覺得是哪一個？」**<br>快、什麼語言都能處理，但 LLM 猜錯了你看不出來 —— 圖上沒有任何記號區分「AST 抓的」和「LLM 猜的」。 |
| **graphify** | **從 AST 做型別推導。**<br>查 `userService` 宣告成什麼 class，順著型別找到那個 class 裡的 method。**推導不出來就不建 edge** —— 寧可漏，不亂連。 |
| **codegraph** | **同樣從 AST 做型別推導，但多走一步。**<br>如果變數宣告成介面，它會再往下找實作 —— 這正是 Spring 專案最需要的那一跳。 |

---

## 1. 怎麼建圖

「三者共通」欄寫三套一致的地方；只要有一套不同，差異就落到各自的欄位。
**真正的分水嶺只有第 3 列**，其他幾列大同小異。

| 比較項目 | 🟰 三者共通 | Understand-Anything | graphify | codegraph |
|---|---|---|---|---|
| **1 · 怎麼解析程式碼** | **三套都用同一套解析器（tree-sitter）**把程式碼拆成 **AST**（抽象語法樹）。<br><br>所以「都是 AST + 靜態分析」這句話對三者都成立 —— **這句話沒有鑑別度**。 | 只有 10 種語言讀得懂。其餘（Kotlin、Swift、PowerShell…）**交給 AI 讀原始碼補** | 語言涵蓋最廣。SQL 要另外裝套件，**沒裝也不會報錯，只是安靜地漏掉** | 安裝最單純（免編譯、跨平台）。**不支援 SQL** |
| **2 · node 怎麼來** | **三套的 node 都是從 AST 的宣告節點抓出來的**：class、method、欄位。<br><br>node id 都帶檔案路徑，所以同名不會撞在一起。 | node 本身是 AST 抓的，**但每個 node 多一段 LLM 寫的說明文字**。<br>好處是用業務術語搜也可能搜到；壞處是那段說明沒人驗證過 | **會讀 `.sql` 檔**，建出資料表、View、預存程序的 node<br>（已實測：Oracle 的 `"SCHEMA"."TABLE"` 格式抓得到） | node 種類最多（24 種，含 API 路由、前端元件）<br>**但沒有資料表 node** |
| **⭐ 3 · edge 怎麼來** | **import edge（檔案之間的引用）三套都是從 AST 確定解析的** —— 這部分都可信。<br><br>差別全在 **calls edge**（A 呼叫 B）上 —— 而那正好是整張圖最有價值的部分。 | 🔴 **calls edge 不是 AST 來的，是 LLM 產生的。**<br>node 用 AST 抓，calls edge 改叫 LLM 猜 —— **同一張圖裡混了兩種來源**。<br><br>給 LLM 的指令原文：「_從 import 和函式名稱**推測**，有信心的話就寫下來_」。<br><br>它連資料結構都撐不住這件事：記錄呼叫的欄位**只有「誰呼叫誰」和行號，沒有欄位能記「對方在哪個檔案」** —— 所以**跨檔案的呼叫它結構上就存不下來**。<br><br>原始碼裡有一個建立跨檔案 calls edge 的函式，但**全專案沒有任何一處呼叫它**。<br><br>最後：**圖上沒有任何記號**能分辨哪條 edge 是 AST 解析的、哪條是 LLM 猜的。 | **從 AST 做型別推導。** `userService` 宣告成什麼 class，就去那個 class 的 AST 找同名 method。<br><br>**型別推導不出來、或同名 method 有好幾個 → 直接不建 edge。**<br><br>每條 edge 都標了信心等級：🟢 確定 / 🟡 推測，**你可以自己過濾**。 | 同樣從 AST 做型別推導，**但多處理了 AST 看不到的「動態」情況**：介面 → 實作、callback 註冊、發訊息 → 收訊息、打 HTTP → 對應的 API。<br><br>這些 edge 會標成 🟡 推測 並記下「在哪一行接起來的」。<br><br>**Spring 專案最需要的就是這一類。** 共 13 種 edge 分開記錄。 |
| **4 · 有沒有用 LLM** | — | **有，三個地方**：① 每個 node 的說明文字 ② **calls edge 本身** ③ edge 的方向<br><br>**三者都沒有標記**，事後分不出來源 | **沒有。** node 和 edge 全部從 AST 產生<br>（只有「幫模組取名字」這個附加功能可選用 LLM） | **沒有。** node 和 edge 全部從 AST 產生 |
| **5 · 存成什麼** | — | 一個 JSON 檔 | 一個 JSON 檔 | **SQLite 資料庫**（可以直接下 SQL 查） |

> **一句話**：三套的 **node 都是 AST 抓的**，這部分沒有差別。
> 差別全在 **calls edge** —— **UA 是 LLM 猜的，另外兩套是從 AST 推導出來的**，
> 而推導的那兩套**都會標出哪些沒把握**。

## 2. 為什麼 edge 這麼難建

上一節說「差別全在 calls edge」。這一節說明**為什麼那條 edge 這麼難**，
以及三套各自走到哪一步就停了。理解這一節，才能判斷一張圖上「查不到」到底代表什麼。

### 建一條 calls edge，其實要走三段

看到 `someVar.findById(id)` 這一行，工具要回答的不是一個問題，是三個：

| | 要回答什麼 | 難在哪 | 結果 |
|---|---|---|---|
| **①** | **推出型別**<br>`someVar` 是什麼型別？ | 要查這個變數的宣告 —— 可能在參數、在欄位、在上面幾行的區域變數 | → `UserRepository` |
| **②** | **型別找到 class node**<br>叫 `UserRepository` 的 class 是哪一個？ | **同名的可能不只一個**（不同 package） | → 唯一的那個 class node |
| **③** | **class 找到 method node**<br>那個 class 裡叫 `findById` 的是哪一個？ | **overload 的話會有好幾個** | → 建立 calls edge ✓ |

**三段每一段都可能斷。** graphify 的原始碼裡就有兩道明確的放棄閘門，
分別卡在第 ② 段（型別名對到多個 class）和第 ③ 段（overload）——
**遇到就直接不建這條 edge**。

### 三套各走到第幾步

| | 走到哪 | 說明 |
|---|---|---|
| **Understand-Anything** | **推 0 步** | **三段全部跳過**，直接問 LLM 最終答案。省掉的不只是型別推導，是整條驗證鏈。 |
| **graphify** | **推 1 步** | 變數 → 它的**宣告型別**。走完三段就停，推不動就不建 edge。 |
| **codegraph** | **推 2 步** | 同樣走三段，**但如果型別是介面，會再走一步找實作**。Spring 的 `@Autowired` 全靠這一步。 |

### 推導會在哪裡斷

以下六種，前兩種最常見。第 ③④ 種**三套都沒做** —— 是共同的天花板。

| 情況 | Java 例子 | 為什麼斷 | 誰過得了 |
|---|---|---|---|
| **⭐ ① 宣告成介面** | `@Autowired`<br>`private UserService userService;`<br>`userService.findById(id);` | 型別**推導成功了**，推到 `UserService`。但那是介面，`findById` 只有簽章沒有實作內容。 | **只有 codegraph** 會再走一步找實作類別。graphify 停在介面。<br>**Spring 專案幾乎全中這一類。** |
| **② overload** | `findById(Long id)`<br>`findById(String code)` | 要選對得比對**參數型別**。 | graphify 直接放棄不建 edge |
| **③ 泛型取值** | `List<User> users;`<br>`users.get(0).getName();` | 讀 `List<User>` 時**只取得到基底型別 `List`**，拿不到裡面的 `User`。（已查證程式碼） | **三套都沒做泛型代換** |
| **④ 回傳值串接** | `getRepository().findById(id);` | 型別表只記「**變數 → 型別**」，**沒有記「method → 回傳型別」**，所以 `getRepository()` 推不出來。 | **三套都沒做** |
| **⑤ 型別不在索引裡** | 第三方 jar、JDK 的 class | 看不到它們的原始碼，找不到對應的 node。 | 都不行（設計如此，不是缺陷） |
| **⑥ 反射** | `Class.forName(name)` | 執行期才決定，靜態分析理論上就不可能。 | 都不行 |

### 不是每種 edge 都需要型別推導

這是常見的誤解。大多數 edge 的目標**字面就寫在那一行**，不用推。
但「寫在那裡」不代表「知道它指向哪一個 node」—— **名字是會撞的**。

| 目標端怎麼來 | 哪些 edge | 風險 |
|---|---|---|
| 🟢 **讀出來**（結構） | `contains` | file 裡有 class、class 裡有 method —— 就是 AST 的巢狀結構。**零風險。** |
| 🟢 **讀出來**（名字寫在那裡） | `imports` `extends` `implements` `instantiates` `decorates` | `extends BaseEntity`、`new UserDTO()` —— 型別名是字面寫著的，**不用推**。<br><br>⚠ 但專案裡可能有三個 `BaseEntity`（在不同 package），**要選對得靠檔案頂端的 import 敘述**。這叫 import 綁定，同樣是一道會斷的關卡。 |
| 🟡 **⭐ 推出來** | `calls`（`x.foo()` 這一類） | 要走完前面那三段。**Java 幾乎所有呼叫都屬於這一類** —— 所以型別推導的品質，基本上就決定了 Java 專案圖的品質。 |
| 🔴 **猜出來** | 裸名字比對、LLM 推測 | **永遠有答案，而且不會告訴你答錯了。** |

> **graphify 明確拒絕「猜出來」那一格**
>
> 它的原始碼註解寫著：缺少或模糊的接收者型別會被**跳過，而不是退回裸方法名比對**。
>
> 另一處在講為什麼要阻擋跨語言比對：「沒有這個，Java 的 `Greeter` 會**很開心地綁到另一個 repo 的同名 Python 類別**。」
>
> 「很開心地」這個用詞很傳神 —— **純名字比對永遠找得到東西，這正是它危險的地方。**

### 回頭看 UA：為什麼會變成這樣

UA 不是偷懶。它的 calls edge 之所以交給 LLM，是一個**架構決定的連鎖結果**：

```
1. 決定「讓 LLM 逐檔分析」
        ↓
2. 每次只看得到一個檔案
        ↓
3. 解析器抓呼叫的資料結構就設計成逐檔的
   —— 只有「誰呼叫誰」和行號，沒有欄位記「對方在哪個檔案」
        ↓
4. 跨檔案的呼叫沒地方存
        ↓
5. 只好在 edge 規格裡寫：
   「這個檔案裡的函式呼叫了另一個檔案的函式 —— 從 import 和函式名稱『推測』」
        ↓
!  原始碼裡有一個建立跨檔案 calls edge 的函式，簽章完全正確
   （四個參數：來源檔、來源函式、目標檔、目標函式）
   —— 但全專案沒有任何一處呼叫它
```

**所以根因是「逐檔分析」這個架構決定**，型別推導只是被連帶犧牲的東西。

這也解釋了一個看似矛盾的現象：**UA 的 import edge 反而做得特別紮實**
（有一支 2000 多行的專用程式處理路徑別名、套件設定檔）——
因為那支程式是**全域跑一次**的，不受逐檔限制。
**同一個專案裡，不受架構限制的部分做得很好，受限制的部分就整段外包給 LLM。**

### ⚠️ 順帶一個陷阱：weight 不是 confidence

UA 的 edge 規格表給每種 edge 一個固定的 weight：

```
imports  → 0.7    ← 來自確定性的 import map，最可信
calls    → 0.8    ← LLM 推測，最不可信
```

**最可信的 edge 權重反而最低。** 因為 weight 是「這種 edge 類型的固定分數」，
跟「這一條是不是真的」完全無關。

如果有人想用 weight 過濾可信度，會**剛好篩掉最可靠的、留下最可疑的**。
這是個很具體的例子：**圖上有數字，不代表那個數字有意義。**

## 3. 怎麼用圖

圖建好之後，AI 助理要怎麼查？
**第 2 列是這張表的樞紐** —— UA 根本沒有查詢工具，
它給的是一份「操作說明」，實際動手的是 AI 自己的搜尋指令。
所以第 3 列之後 UA 沒東西可填。

| 比較項目 | 🟰 三者共通 | Understand-Anything | graphify | codegraph |
|---|---|---|---|---|
| **1 · 有沒有使用說明** | **三者都有**，都附了給 AI 助理看的操作說明文件。 | 一份 70 行的說明 | 說明裡有 300 多行**專門在教「關鍵字要怎麼下」** | 說明會**自動塞進 AI 的記憶**，AI 想不看都不行 |
| **⭐ 2 · 有沒有內建查詢工具** | — | ❌ **沒有**<br>建圖有 12 支程式，**查圖一支都沒有**。<br><br>說明文件教 AI 這樣做：① 用搜尋指令在 JSON 裡找關鍵字 ② 把找到的 ID 再搜一次，撈出相連的東西<br><br>**執行的是 AI 自己的工具，不是 UA 的程式。** | ✅ **有**<br>10 個查詢工具 + 28 個指令<br><br>**主要入口：`query_graph`**<br><br>其他 9 個都要你**已經知道名字**才能用 | ✅ **有**<br>8 個查詢工具 + 網頁介面<br><br>**主要入口：`codegraph_explore`**<br><br>說明裡直接寫「**只有這一個工具**」 |
| **3 · 查的時候要給什麼** | — | —（無工具，見上列） | 一句問題或關鍵字<br>＋ 要找幾層（1–6）<br>＋ 回傳長度上限<br>＋ **只走哪幾種 edge**（例如只走 calls） | 一句問題、或直接丟幾個名字、**或丟檔案路徑**<br>＋ 要幾個檔案（1–20） |
| **4 · 怎麼找到起始 node** | **三套都是關鍵字比對，沒有任何一套用語意搜尋。**<br><br>意思是：**你的關鍵字要跟程式碼裡的英文名稱對得上**。用中文業務術語查，三套都會落空。 | —（AI 自己下搜尋條件） | 拆詞較單純。<br><br>⚠ 有個副作用：**問題裡的詞越多，起始 node 就越多**，容易發散 | 拆詞最細（會拆 `OrderStateMachine` → order / state / machine），所以**模糊一點的問法也命中得到** |
| **⭐ 5 · 從起始 node 怎麼擴散** | **走 edge 時不分方向**：不管「誰呼叫它」還是「它呼叫誰」都算相關。<br><br>三套都這樣做，因為只往下走的話，**最底層的 method 會查出空的**。edge 的方向要到「講答案」的時候才恢復。 | —（只看直接相連的一層，不排序） | 往外找 3 層。<br><br>**共用 node 的處理**：碰到「被 50 個以上地方連到」的 node 就**停住不再往外走**。<br><br>⚠ **但這道防線有漏洞** —— 如果那個共用 node 剛好被選成起始 node，它就不受限制，**結果會爆量** | 往外找 3 層，另外**特別補上繼承關係和中間的橋接節點**。<br><br>**共用 node 的處理**：用數學方式稀釋 —— 一個連到 300 個 node 的元件，**分給每個鄰居的相關度只有 1/300**，自然就沉下去了。<br><br>排序看的是 **edge 上的實際呼叫關係**，不是名字像不像 |
| **⭐ 6 · 最後回傳什麼** | — | —（搜尋指令找到的那幾行 JSON。因為排版關係，還要再讀一次檔案才拿得到上下文） | **一份 node 清單**：有哪些 node、在哪個檔案第幾行。<br><br>**沒有原始碼。**<br><br>→ AI 還要**自己去讀檔案** | **一份報告**：<br>① 呼叫鏈（A → B → C）<br>② 影響範圍（誰依賴它、有沒有測試）<br>③ **最多 8 個檔案的原始碼，逐字帶行號**<br>④ 沒給你的檔案清單<br><br>→ AI **直接回答** |
| **7 · 可以調什麼** | — | —（AI 自訂搜尋條件，自由度最高但沒有護欄） | 層數、回傳長度、**只走哪幾種 edge**<br><br>**「只走 calls edge」是 codegraph 做不到的** | **只有「回傳幾個檔案」。**<br><br>排除某個目錄、只走某種 edge、改層數 —— **全部做不到**，只能換個問法重試 |

## 4. 三個實際踩到的坑

這三個都是實際操作驗證過的，不是理論推測。分享時值得提，因為它們說明一件事：
**全自動建出來的圖，有些缺失是看不出來的。**

### ⚠️ 坑 1 — 圖上查不到，不代表真的沒有

我拿一份典型的 Oracle DDL 測 graphify：三張表都建出來了，**但外鍵一條都沒有**。

原因不是資料庫沒有外鍵，而是**解析器看不懂 `VARCHAR2` 和 `NUMBER(10,0)`** 這些
Oracle 專有寫法，整個欄位區塊解析失敗，寫在裡面的外鍵一起消失。

**最麻煩的是它不會報錯** —— 表的數量完全正常，你不會知道少了什麼。
（已寫好前處理腳本可修正。）

### ⚠️ 坑 2 — 「找不到路徑」可能只是方向記反了

graphify 查兩點之間的路徑時，**預設只往一個方向找**。找不到會回「沒有路徑」。

但依賴注入、callback 註冊這類關係，**該記哪個方向本來就是模糊地帶**。
工具記反一條，查詢就直接說「沒有」。

**實務規則：查不到時先換成「不分方向」再試一次，才能下結論。**

### ⚠️ 坑 3 — 查詢結果沒有先後順序

查出來的那串 node，**只代表「這些跟你問的有關」，不代表執行順序**。
「A 和 B 相關」不等於「A 呼叫 B」。

要順序得另外查：graphify 用「最短路徑」功能，codegraph 看報告開頭的呼叫鏈。
**別讓 agent 從 node 清單自行推論流程。**

---

## 結論

### Understand-Anything — node 是 AST 的，edge 是 LLM 的

適合「快速認識一個沒碰過的 repo」。
**不適合任何需要「不會漏」的場合** —— 因為 calls edge 是 LLM 猜的，而且你分不出哪些是。

### graphify — 寧可漏，也不亂連

唯一有信心分級的。適合**看架構全貌**（有模組分群、核心元件排行、PR 影響分析）。
代價是 agent 拿到 node 清單後還要自己讀程式碼。

### codegraph — 直接把答案和原始碼一起給你

適合**追一條具體的鏈路**、問「改這裡會影響誰」。
省來回、答得準，代價是**幾乎沒有旋鈕可以調**。

---

## 真正的差別：把多少判斷交給 AI

三套的差別不在「誰的圖比較準」，而在**把哪些判斷交給 LLM**。
交得越多，彈性越大、但錯了越沒有痕跡；交得越少，答案越穩、但你越無法客製。

```
工具說了算                                           LLM 說了算
兩個參數，回傳成品                              自訂搜尋，自行推論
    │                                                      │
    ▼                                                      ▼
codegraph ──────────── graphify ──────────── Understand-Anything
```
